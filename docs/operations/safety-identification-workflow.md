# Optional scoped identification requests

This workflow lets a Site Safety Officer ask the current assigned Site Manager to help identify the exact subject of an existing safety episode. Tracker IDs and AI candidates are not verified Worker identity. An Officer reviews the Manager proposal; accepting it closes the identification request only. It does not grant Zone access, change Face consent, confirm an incident or notify a Contractor automatically. A subsequent corrective handover uses the existing separately authorized incident command.

The endpoints are disabled by default (`SAFETY_IDENTIFICATION_ENABLED=false`). Enabling requires an explicitly reviewed `DATABASE_SCHEMA` and `SMARTSITE_DB_MIGRATION_PROFILE=tracked-v16-identification`. This profile extends the reviewed tracked-v16 profile with the two approved C02 tables (`safety_identification_request`, `safety_identification_action`, migration `1795046400009`). It does not install unrelated MF06 permission-history migrations. Automatic migrations and synchronization remain disabled. Source integration does not authorize modifying an operational website database.

Requests retain subject/episode/Site binding, command replay, version checks and append-only history. Access is evaluated against current account/session, Site role and assigned Manager on each operation. Reassignment or grant removal revokes former assignee access. Manager outcomes may be identified, partial, unresolved or disputed; a proposal remains a human claim with provenance. Officer acceptance rechecks the current Worker/Contractor scope.

Published subject evidence requires Officer review and explicit approval of the derivative preview. Requests without approved evidence report unavailable. Image bytes and source digests are checked; only the assigned request scope can read the published image, within its expiry. A general camera frame or an internal Face crop is not automatically available to the Manager. The retention tool defaults to inventory; deletion is restricted to the owned local test target. It must not be run against website or cloud storage as part of source verification.

Rehearse the exact profile, fresh/upgrade/rollback guards, current-role HTTP lifecycle, replay/conflict, image masking/digest/expiry and request-specific media access using the dedicated loopback PostgreSQL test database on 5433. Source, synthetic test and browser rendering proofs are separate from production acceptance. Rollout needs an explicit target, backup and retention/rollback review.
